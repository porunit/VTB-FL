# ТЗ — Горизонт H1 «Учёт сам»

Первый горизонт оцифровки: единый учёт + карточка водителя + ручной ввод платежа + авто-расчёт долга + конвейер задач сборщикам + флаги/комментарии + дашборд. **Цель H1 — убрать ручной труд вокруг учёта, оставив ручной только сам ввод платежа.**

## 1. Границы

**В скоупе H1:**
- Карточка водителя (агрегат по дата-модели).
- Ручной ввод платежа (нал/безнал) — **одна отметка**, без подтверждений.
- Авто-расчёт долга по водителю и общего после каждого платежа.
- Конвейер задач сборщикам с основанием и документами (генерация/закрытие/эскалация).
- Флаги состояния (`авария/рассрочка/не трогать/спор`) и комментарии.
- Дашборд реалтайм (расширение существующего).
- Импорт из текущей Google-таблицы.
- Уведомления (базовые) — можно заглушкой/в один канал.

**Вне скоупа H1 (это H2+):**
- Удержание в Яндекс.Fleet (рычаг) — отдельный трек после разведки API и юр-оформления.
- Авто-сбор штрафов из «Моя ГИБДД».
- Авто-атрибуция безнала из банковской выписки.
- FastPay-списания, CX-анализ, фин-модель.

## 2. Роли (RBAC)

| Роль | Может |
|---|---|
| `operator` (Серёга) | вводить платежи, ставить флаги/комменты, видеть всё |
| `collector` (Слава/Женя) | видеть свои задачи, отмечать «принял нал» → платёж |
| `owner` (инвестор) | дашборд, отчёты, read-only по всему |
| `admin` | пользователи, договоры, машины, импорт |

## 3. Функциональные требования

### 3.1 Карточка водителя
- Просмотр: договор(ы), машина, баланс, история платежей, начисления, штрафы, флаги, документы, комментарии.
- Редактирование договора/машины/залога (admin).

### 3.2 Ввод платежа (ядро)
- Форма: водитель, сумма, канал (`cash/card/fastpay`), дата, чек (опц.), комментарий.
- **Одна отметка, без подтверждения второго лица.**
- При сохранении ⚙️: распределение по открытым начислениям (FIFO/по выбору), пересчёт баланса, закрытие/обновление связанной задачи, событие в шину (для уведомлений/дашборда).

### 3.3 Авто-расчёт долга
- `balance(driver) = Σ open charges`. Пересчёт мгновенный.
- Помесячная разбивка, aging, статус-светофор, дни без оплаты — как в текущем дашборде, но из БД.
- Ежедневное/ежемесячное авто-начисление CHARGE по договору (аренда — суточно, выкуп — по графику).

### 3.4 Конвейер задач сборщикам
- ⚙️ Генерация TASK по правилу: есть просроченный остаток И нет блокирующего флага → создать/обновить задачу (сумма, основание = charge_ids, документы, приоритет по величине/возрасту долга).
- Назначение (Слава/Женя), статусы, SLA, авто-эскалация при просрочке SLA.
- Закрытие задачи автоматически при поступлении платежа, гасящего основание.
- **Не «список должников», а самоуменьшающийся набор задач.**

### 3.5 Флаги и комментарии
- Поставить флаг (`авария` и т.п.) с причиной и сроком → блокирует генерацию задач (и позже — удержаний).
- Комментарий к платежу/водителю; 🤖 авто-классификация комментария → предложение создать флаг (можно вручную на H1).

### 3.6 Дашборд
- Существующий (KPI, динамика, матрица, водители) — переключить источник с листа на API/БД.
- Добавить: задачи в работе, сколько на флагах, собрано за период.

### 3.7 Импорт
- Загрузка из текущей Google-таблицы → CHARGE/PAYMENT; сверка `Осталось` с расчётным балансом (контроль миграции: должно сойтись, как сверяли −5 055 523).

## 4. Нефункциональные требования / стек

- **Цель-стек** (по встрече): Java/Spring Boot + PostgreSQL + RabbitMQ (шина событий) + бот (Telegram/MAX). REST API + веб-фронт.
- **Прагматичный старт:** существующий Python/FastAPI-дашборд переиспользуется как read-view, либо H1 сразу на целевом стеке, а дашборд переносится. Решение — отдельно (см. вопрос ниже).
- Аудит-лог всех изменений (кто/что/когда) — для прозрачности и споров.
- Аутентификация + роли; HTTPS (уже есть на сервере).
- Реалтайм-обновление дашборда (polling 60с — как сейчас; позже SSE/WS).
- Бэкапы БД.

## 5. Ключевые пользовательские сценарии

1. **Приём нала** → оператор/сборщик жмёт «принял нал», вводит сумму → ⚙️ долг пересчитан, задача закрыта, дашборд обновлён, водителю ушло уведомление. *(одна отметка)*
2. **Авария** → оператор ставит флаг `accident` → ⚙️ задачи по водителю не генерятся, удержания (в H2) не ставятся.
3. **Генерация работы сборщику** → утром у Славы/Жени список задач с суммами, основаниями и документами; по ходу дня закрываются платежами.
4. **Просмотр карточки** → вся история водителя в одном месте.
5. **Импорт/сверка** → загрузить лист, убедиться, что баланс сошёлся с «Осталось».

## 6. Критерии приёмки

- [ ] Ввод платежа в один шаг пересчитывает баланс и закрывает задачу < 1с.
- [ ] Сумма балансов по водителям = контрольному итогу из листа (сверка сходится до рубля).
- [ ] Флаг `accident` доказуемо блокирует генерацию задач.
- [ ] Задачи генерятся/эскалируются по правилам; нет ручного ведения «списка».
- [ ] Дашборд работает на БД, метрики совпадают с прежними.
- [ ] Аудит-лог фиксирует каждое изменение.

## 7. Этапность внутри H1

1. БД + импорт из листа + расчёт баланса (сверка). *(переиспользует готовый парсер)*
2. Форма ввода платежа + карточка водителя.
3. Конвейер задач + флаги/комменты.
4. Дашборд на БД + уведомления (базовые).

## 8. Открытый вопрос для старта

**Стек H1:** продолжаем на Python/FastAPI (быстрее, дашборд готов) или сразу строим целевой Java/Spring + Postgres + RabbitMQ (по встрече, под бота и масштаб)? От этого зависит структура H1-репозитория.
