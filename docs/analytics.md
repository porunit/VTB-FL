# Блок учёта и аналитики — спецификация (идеальный результат)

> Что показывает система собственнику, оператору и сборщику. Опирается на схему
> [db-schema.md](db-schema.md) и принципы [ИКР.md](ИКР.md).
> Решения по ключевым развилкам зафиксированы с собственником (см. раздел 0).

---

## 0. Зафиксированные решения

1. **Главная цифра дашборда — «Общий долг незабранных денег»**, рядом — «Собрано за месяц vs план». Ведём сырой суммой того, что должны, а не взвешенным прогнозом.
2. **Замороженный долг (авария/болезнь) считается ВНУТРИ общего долга**, но визуально помечен причиной. Не вычитаем и не прячем — это измерение-фильтр, а не отдельная сумма.
3. **Касса сборщика / «деньги в пути» — НЕ отслеживаем.** Сборщик не имеет денежного понятия в системе вообще; деньги = только журнал оператора. Один контур.

---

## 1. Два слоя: учёт ≠ аналитика

- **Учёт** — факт, неоспоримая истина (журнал, балансы). Нет интерпретаций.
- **Аналитика** — выводы поверх факта (KPI, прогнозы, сегменты, рейтинги).

## 2. Учёт (факт)

| Блок | Содержание | Источник в схеме |
|---|---|---|
| **Журнал платежей** | каждая транзакция: дата, водитель, месяц, сумма, источник (наличка/выкуп/удержание/возврат), кто внёс (оператор), кто принёс (сборщик, информац.) | `payments` |
| **Баланс (водитель × месяц)** | obligation / paid / balance / status / reason — матрица-хитмап | `v_rental_month_balance` |
| **Книга по машине** | доход на машину, выкупы, простой | `payments` → `car_id` |

## 3. Шапка KPI (что видно первым)

```
┌─────────────────────────┬──────────────────────────┐
│ 🔴 ОБЩИЙ ДОЛГ            │ 🟡 СОБРАНО ЗА МЕСЯЦ       │
│    незабранных денег     │    1.2М / план 1.8М (67%)│
│    3 450 000 ₽           │    ▲ +12% к прошлому      │
│    из них заморожено 280k│                          │
├──────────┬──────────┬────┴──────────┬───────────────┤
│ Должников│ Просрочка│ Средний долг  │ Собрано сегодня│
│   23     │ 2+ мес   │  на должника  │   145 000 ₽    │
└──────────┴──────────┴───────────────┴───────────────┘
```

### Формулы KPI

| KPI | Формула |
|---|---|
| **Общий долг** | `Σ −balance` по всем `rental_months` где `balance < 0` (закрытые + текущий) |
| ↳ из них заморожено | то же, но `WHERE reason IN ('accident','illness') AND status='frozen'` |
| **Собрано за месяц** | `Σ payments.amount` где `paid_at` в текущем месяце, `source IN ('cash','buyout')` |
| **План (pro-rata)** | `Σ obligation` текущего месяца × (прошло дней / дней в месяце) |
| **Собираемость %** | собрано за месяц / план pro-rata (cap 100%) |
| **Должников** | `COUNT(DISTINCT driver_id)` где есть `rental_month` с `balance < 0` |
| **Просрочка 2+ мес** | `Σ −balance` по водителям с ≥2 закрытыми месяцами подряд с долгом |
| **Средний долг** | общий долг / должников |
| **Собрано сегодня** | `Σ payments.amount` где `paid_at = current_date` |

**Замороженный долг** — сквозной фильтр-измерение: в общем долге учтён, но в любом виджете есть переключатель «показать/скрыть заморозку» и виден бейдж причины.

## 4. Аналитика по горизонтам

Каждый горизонт = свой тип решения и свой потребитель.

### 🔴 Операционный (сегодня / неделя) — оператор и сборщик

| Виджет | Решение, на которое отвечает | Логика |
|---|---|---|
| **Приоритет сбора** | «кого дёргать сейчас» | сортировка по `(−balance) × давность`; замороженные внизу с бейджем |
| **Маршрут сборщику** | «к кому ехать» | долги по месяцам + договор-основание (`documents.is_collection_basis`) + полевой статус |
| **Обещали сегодня** | «кому напомнить» | `collection_tasks` где `promised_date = current_date`, `field_status='promised'` |
| **Свежие срывы** | «кто только что перестал платить» | водители с `last_payment_date` старше N дней, кто раньше платил регулярно |

### 🟡 Тактический (месяц) — собственник, управление

| Виджет | Логика |
|---|---|
| **Собираемость vs план** | линия собрано / pro-rata план по дням месяца + тренд к прошлым месяцам |
| **Прогноз закрытия месяца** | `собрано_на_сегодня / доля_прошедших_дней`, скорректированный на исторический «хвост» месяца |
| **Воронка сбора** | должны → в работе (`collection_tasks`) → обещали → принесли → проведено (`payments`) |
| **Сегменты должников по причине** | разбивка общего долга: живой / 1 мес / 2–3 мес / 3+ / заморожено |

### 🟢 Стратегический (тренды, масштаб) — собственник, рост

| Виджет | Логика |
|---|---|
| **Доход на машину** | `Σ payments` по `car_id` / число активных месяцев; рейтинг машин, % простоя |
| **Lifetime водителя** | `Σ payments` водителя за всё время + индекс дисциплины (доля месяцев, закрытых в срок) |
| **Дисциплина сборщика** | обещал (`collection_tasks.promised_amount`) vs реально принёс (`payments.collector_id`); конверсия и скорость |
| **Потери** | списано / безнадёжный долг (3+ мес, `malicious`) / % невозврата по парку |

## 5. Метрики, требующие договорённости (черновые формулы)

**Прогноз закрытия месяца.**
База: `прогноз = собрано_на_сегодня / (прошло_дней / дней_в_месяце)`.
Уточнение: домножить на исторический коэффициент «хвоста» — в этом бизнесе платежи часто идут неравномерно (крупные суммы к концу месяца, выкупы). Коэффициент = средняя доля сбора за оставшиеся дни по прошлым месяцам.

**Индекс дисциплины водителя.**
`закрытых_в_срок_месяцев / всего_месяцев_аренды`. «В срок» = `balance ≥ 0` к концу месяца. От 0 до 1; рядом — средняя задержка платежа в днях.

**Дисциплина сборщика.**
`принесено / обещано` за период (конверсия обещаний в деньги) + средний лаг между `collection_tasks.promised_date` и фактическим `payments.paid_at`.

## 6. Как это растёт по этапам

| Этап (из ИКР) | Что из аналитики появляется |
|---|---|
| 1. Оператор-ввод | журнал платежей, баланс, шапка KPI (на данных БД) |
| 1b. Причины/заметки | сегменты по причине, замороженный долг как фильтр |
| 2. Бот сборщика | приоритет сбора, маршрут, воронка, полевые статусы |
| 3. Аналитика | прогноз закрытия, lifetime, доход на машину, дисциплина сборщика |
| 4–5. Яндекс/таксометр | потери от штрафов, эффект удержаний |
