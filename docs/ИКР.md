# Идеальный Конечный Результат (ИКР) системы учёта лизингового парка

> Методология: ТРИЗ. Документ описывает целевое (идеальное) состояние системы,
> ключевые противоречия бизнеса и их разрешение, целевую модель данных и акторов,
> и поэтапную дорожную карту от текущего дашборда к ИКР.

---

## 0. Контекст бизнеса

Лизинговая компания сдаёт автомобили водителям в аренду и собирает с них
**наличные** платежи. У каждого водителя — помесячное обязательство (аренда),
платежи приходят нерегулярно. Сбор денег физически ручной (наличка), всё
остальное подлежит оцифровке и систематизации ради прозрачности и масштабирования.

### Текущее состояние системы (на момент написания)
- **Стек:** Python 3.12 + FastAPI (backend), vanilla JS + Chart.js (SPA), данные — Google Sheets (read-only), деплой Docker + Caddy на Vultr VPS, CI/CD через GitHub Actions.
- **Данные** живут в Google-таблице `ПЛАТЕЖИ 2026`: месячные блоки, поставленные вертикально (Январь→…→6 блоков). Каждый блок:
  - `Сумма/сутки` — дневная ставка по каждому водителю (колонка на водителя, ~50 водителей);
  - `сумма мес.` — обязательство за месяц (отрицательное, напр. −99000);
  - `Номер авто` — привязка машины;
  - дневные строки 1–31 — приходы наличкой по дням;
  - `Итого` — собрано за месяц; `Осталось` — остаток по месяцу (отриц. = не закрыт).
  - Отдельные потоки: `ВЫКУП` (выкуп авто), `КОНТРОЛЬ`.
- **Что умеет:** только отображение — динамика долга, матрица-хитмап (водитель×месяц), таблица водителей, drill-down модалки, aging, собираемость, CSV-экспорт. **Записи, ботов, интеграций, пометок — нет.**

**Ключевой вывод:** месяц — это уже естественный расчётный период бизнеса, а `Осталось` по месяцу = «закрыл/не закрыл». Поэтому привязка неуплаты к месяцу — не натяжка, а отражение того, как бизнес уже устроен.

## 1. Главная полезная функция (ГПФ)

> **Превращать парк автомобилей в стабильный, предсказуемый и прозрачный денежный
> поток — при минимальных потерях (неплатежи, штрафы, простой) и минимальном
> ручном труде, не разрушая лояльность водителей.**

### Формула идеальности

```
                 Σ собранных денег + прозрачность + масштабируемость
Идеальность  =  ─────────────────────────────────────────────────────
                 ручной труд + потери (долги, штрафы) + конфликты с водителями
```

Критерий для любой фичи: **увеличивает числитель или уменьшает знаменатель?**
Если нет — фича не нужна.

## 2. Формулировка ИКР (3 уровня)

**Радикальный ИКР** («системы нет, а функция выполняется»):
> Водитель платит сам и вовремя, потому что не платить ему невыгодно и неудобно
> (долг сам удерживается с таксометра), а система лишь фиксирует факт. Сборщик
> нужен только там, где физически передаётся наличка — всё остальное само.

**Рабочий ИКР** (то, к чему строим):
> Каждый рубль обязательства, платежа, штрафа и удержания фиксируется в момент
> возникновения, без ручного ввода в таблицы. Система сама решает «с кого требовать
> сейчас, кого подождать, кого отпустить», сама готовит сотруднику маршрут с
> документами-основаниями, а собственник в любой момент видит прозрачную картину:
> кто сколько должен, почему, и сколько реально вернётся.

**ИКР по подсистемам** — каждый X-элемент «делает работу сам»:

| X-элемент | Сам выполняет функцию |
|---|---|
| Таксометр | сам удерживает долг и возвращает деньги после оплаты — без сборщика |
| Система | сама классифицирует неплатёж: авария / болезнь / забыл / тянет / злостный |
| Штраф | сам списывается через диспетчерскую Яндекс при пометке «в парке» |
| Сборщик | получает готовый список: к кому ехать, сколько забрать, за какой месяц, на каком основании (договор) |
| Оператор | единственная точка ввода денег → денежная истина герметична |

## 3. Ключевые противоречия и их разрешение (ядро ТРИЗ)

### ⚔️ Противоречие 1. «Наличка собирается только руками» vs «всё автоматизировано»
- **Физическое противоречие:** акт сбора денег ДОЛЖЕН быть ручным (наличка, доверие, контакт) И ДОЛЖЕН быть автоматическим (скорость, масштаб, прозрачность).
- **Разрешение — разделение в пространстве** (дробление): ручным остаётся только физический момент передачи купюр. Всё вокруг — назначение долга, фиксация, документ-основание, контроль, аналитика — отделяется и автоматизируется.
- **Важно:** деньги в систему вносит НЕ сборщик, а **оператор** — после получения налички от сборщика. Источник денежной истины один.

### ⚔️ Противоречие 2. «Давить на должника» vs «не давить»
- Нужно жёстко возвращать деньги И нельзя грузить человека в аварии (он лоялен, вернётся).
- **Разрешение — контекстная сегментация по причине неплатежа** (местное качество): статус долга = не просто «красный», а `авария / болезнь / забыл / тянет / злостный`, привязанный к конкретному месяцу. Аварийному — пауза и заморозка (долг виден, но выпадает из давления), злостному — удержание + выезд.

### ⚔️ Противоречие 3. «Водитель должен работать» vs «нельзя дать работать в долг»
- Чтобы заплатить, водитель должен ездить и зарабатывать. Но ездит и не платит → долг растёт.
- **Разрешение — градуированное удержание вместо блокировки**: не отключаем водителя (потеря дохода для всех), а удерживаем процент с таксометра. Работает, долг гасится сам, после погашения удержание снимается.

### ⚔️ Противоречие 4. «Штраф пришёл на компанию» vs «виноват водитель»
- Штрафы с камер приходят на юрлицо-собственника, нарушал водитель.
- **Разрешение — связка «пометка в парке» → автосписание** (обратная связь): если в момент штрафа водитель помечен «в парке/на линии», система формирует основание и списывает сумму через диспетчерскую Яндекс, фиксируя транзакцию.

## 4. Модель акторов (разделение полномочий)

| Актор | Что МОЖЕТ | Чего НЕ может |
|---|---|---|
| **Оператор** | единственный, кто **создаёт платёж** (сумма, дата, от кого, за какой месяц); загружает договоры к водителям | — |
| **Сборщик** (бот) | видит свой список: кого, сколько, за какой месяц, **+ договор-основание**; ставит полевой статус (был / обещал / отказался / нет на месте) | **не вводит деньги** — отметки не двигают баланс |
| **Собственник** | видит всё: аналитику, прозрачную картину | — |

**Принцип:** полевая активность сборщика и денежная истина — два разных слоя.
Сборщик генерирует «обещания и контакты», оператор — подтверждённые рубли.
Они сверяются, но не смешиваются.

**Поток документов** однонаправленный: оператор загружает **договор водителя** →
он показывается **сборщику** как юридическое основание для забора денег.
(Отдельный «бот должника» не нужен.)

## 5. Целевая модель данных

Главный барьер к ИКР: Google-таблица не умеет принимать записи и хранить связи.
Ядро эволюции:

```
Google Sheet (read-only)  ──►  Postgres + событийный журнал транзакций
```

Базовая единица учёта — пара **(водитель × месяц)**:

```
Driver {
  id, name, car, phone,
  inPark,            // пометка «в парке/на линии» — для списания штрафов
}

Car { id, plate, dailyRate, driver }

DriverMonth {            // единица учёта обязательства за месяц
  driver, month, car,
  obligation,            // сумма мес. (−99000)
  paid,                  // сумма подтверждённых платежей оператора
  remaining,             // = obligation + paid → закрыт / долг
  status,                // closed / debt
  reason,                // авария / болезнь / забыл / тянет / злостный
  note,                  // заметка с датой
}

Payment {                // журнал, создаёт только оператор
  driverMonth, amount, date, operator, source,  // наличка / выкуп / удержание
}

Document {               // договор-основание
  driver, type,          // договор аренды / доп.соглашение / расписка
  file, isCollectionBasis,
}

CollectionTask {         // задача сборщику (read-only по деньгам)
  driver, debtByMonth, document, fieldStatus,    // был / обещал / отказ / нет
}
```

Соответствие текущей таблице:
- `сумма мес.` → `DriverMonth.obligation`
- дневные приходы → `Payment` (агрегируются в `DriverMonth.paid`)
- `Осталось` → `DriverMonth.remaining`
- накопленный долг = Σ `remaining` по закрытым месяцам (бэкенд уже считает как `closedBalance`)
- `ВЫКУП` → `Payment.source = выкуп`

## 6. Дорожная карта к ИКР

Порядок по принципу «максимальный рост идеальности за минимальную цену».

| Этап | Что | Закрывает | Сложность |
|---|---|---|---|
| **0. БД-фундамент** | Postgres, перенос месячных блоков в `DriverMonth` + журнал `Payment`. Чтение из таблицы пока оставить | без этого ничего не записать | средняя |
| **1. Оператор-ввод** | панель оператора: внести платёж (сумма/дата/месяц), редактировать обязательства, **загрузка договоров** к водителям | учёт денег, единая точка ввода | средняя |
| **1b. Заметки и причины** | `reason` + заметки на (водитель×месяц) | пометки, «не грузить аварийного» | низкая |
| **2. Бот сборщика** | список долгов по месяцам + **договор-основание** + полевые статусы. Read-only по деньгам | систематизация ручного сбора, основания | средняя |
| **3. Расширенная аналитика** | прогноз возврата, сегменты должников, сверка «обещал vs заплатил», дисциплина сборщика | расширить аналитику, прозрачность | низкая (данные уже есть) |
| **4. Интеграция Яндекс** | пометка «в парке» → автосписание штрафа | противоречие №4 | высокая (внешний API) |
| **5. Удержание с таксометра** | автоудержание долга и возврат после оплаты | противоречие №3, радикальный ИКР | высокая |

**Логика порядка:** этапы 0–2 дают полную оцифровку и систематизацию ручного
сбора (главная цель — масштабирование), денежный контур герметичен (один ввод,
оператор). Этапы 4–5 — «система сама собирает деньги», самые мощные, но зависят
от внешних API (Яндекс, таксометр), поэтому позже.
